# API Contracts (Контракты взаимодействия Frontend - Backend)

В данном документе описаны все внешние HTTP эндпоинты платформы, проксируемые через **API Gateway**, а также WebSocket-протоколы и внутреннее взаимодействие.

# GET /health
## Описание endpoint`а, часть бизнес-логики
Простой эндпоинт для проверки работоспособности (Health Check) самого API Gateway. Используется для мониторинга аптайма шлюза без затрагивания внутренних микросервисов.
## Пример запроса
- **Метод**: `GET`
- **Путь**: `/health`
- **Заголовки**: Не требуются
- **Тело запроса**: Отсутствует
## Пример ответа
- **Статус**: `200 OK`
- **Тело ответа**:
```json
{
  "status": "API Gateway is running"
}
```
## Важные нюансы
- Вызывается без авторизационного заголовка (`Authorization: Bearer ...`).
- Не проксирует запросы во внутренние сервисы, а отвечает мгновенно на уровне шлюза.

# GET /api/csrf-token
## Описание endpoint`а, часть бизнес-логики
Получение короткоживущего CSRF токена (срок действия — 5 минут) в виде JWT токена. Используется фронтендом перед отправкой форм обратной связи (feedbacks) для защиты от спама и DDoS.
## Пример запроса
- **Метод**: `GET`
- **Путь**: `/api/csrf-token`
- **Заголовки**: 
  - `Authorization: Bearer <JWT_TOKEN>` (обязательный)
- **Тело запроса**: Отсутствует
## Пример ответа
- **Статус**: `200 OK`
- **Тело ответа**:
```json
{
  "csrfToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```
## Важные нюансы
- Требуется авторизация пользователя.
- В сгенерированный токен зашиваются `userId` и специальный флаг назначения `purpose: 'csrf'`.
- Токен действителен строго в течение 5 минут. По истечении этого времени при попытке отправить форму вернется ошибка `403`.

# POST /api/users/register
## Описание endpoint`а, часть бизнес-логики
Регистрация нового пользователя на платформе. Содержит комплексную защиту:
1. **Проверка reCAPTCHA v3**: Защита от ботов и спам-регистраций.
2. **Проверка силы пароля**: Пароль должен соответствовать требованиям безопасности (минимум 3 из условий: 8+ символов, заглавная, строчная буква, цифра, спецсимвол).
3. **Проверка доставляемости почты (DNS MX check)**: Блокирует временные почтовые ящики и проверяет реальное существование почтового домена с помощью DNS.
4. **Email-верификация**: Создается верификационный токен (на 15 минут), и пользователю отправляется ссылка для подтверждения на почту. До подтверждения почты вход в аккаунт заблокирован.

## Пример запроса
- **Метод**: `POST`
- **Путь**: `/api/users/register`
- **Заголовки**:
  - `Content-Type: application/json`
- **Тело запроса**:
```json
{
  "username": "ivan_ivanov",
  "email": "ivanov@gmail.com",
  "password": "StrongPassword123!",
  "recaptchaToken": "03AFcWeA7..."
}
```
## Пример ответа
- **Статус**: `201 Created`
- **Тело ответа**:
```json
{
  "message": "Пользователь успешно зарегистрирован. На указанный email отправлено письмо для подтверждения аккаунта.",
  "user": {
    "id": 42,
    "username": "ivan_ivanov",
    "email": "ivanov@gmail.com",
    "role": "Standard",
    "is_verified": false
  }
}
```
## Важные нюансы
- Роль по умолчанию устанавливается в `'Standard'`.
- Если reCAPTCHA классифицирует активность как бота (score < 0.5), вернется ошибка `400`.
- Запрещена регистрация с одноразовых доменов (например, `mailinator.com`, `yopmail.com`).
- Происходит фоновый запуск отправки письма, чтобы не задерживать ответ сервера.

# GET /api/users/verify-email
## Описание endpoint`а, часть бизнес-логики
Подтверждение адреса электронной почты пользователя при клике по ссылке из письма. Активирует аккаунт, позволяя входить на платформу.
## Пример запроса
- **Метод**: `GET`
- **Путь**: `/api/users/verify-email?token=32_byte_hex_token`
- **Заголовки**: Не требуются
- **Параметры запроса (Query)**:
  - `token`: Уникальный токен верификации
- **Тело запроса**: Отсутствует
## Пример ответа
- **Статус**: `302 Found` (Redirect)
- **Заголовки**:
  - `Location: http://localhost:8000/login?verified=true`
- **Тело ответа**: Отсутствует (происходит редирект)
## Важные нюансы
- Эндпоинт открывается в браузере напрямую.
- При успешной валидации токена статус `is_verified` пользователя меняется на `TRUE`, а токен сбрасывается в `NULL`.
- В случае недействительного или просроченного токена отдается HTML-страница ошибки верификации со статусом `400`.

# POST /api/users/login
## Описание endpoint`а, часть бизнес-логики
Авторизация пользователя в системе. Проверяет корректность учетных данных, а также накладывает фильтры безопасности:
1. **Проверка бана**: Если пользователь временно или перманентно заблокирован, вход не допускается.
2. **Проверка подтверждения почты**: Если почта не верифицирована, возвращается специальный флаг `emailUnverified` для фронтенда с предложением повторной отправки.
3. **Генерация токена**: При успешном входе генерируется JWT (на 24 часа).

## Пример запроса
- **Метод**: `POST`
- **Путь**: `/api/users/login`
- **Заголовки**:
  - `Content-Type: application/json`
- **Тело запроса**:
```json
{
  "email": "ivanov@gmail.com",
  "password": "StrongPassword123!"
}
```
## Пример ответа
- **Статус**: `200 OK`
- **Тело ответа**:
```json
{
  "message": "Успешный вход",
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "user": {
    "id": 42,
    "username": "ivan_ivanov",
    "email": "ivanov@gmail.com",
    "role": "Standard"
  }
}
```
## Важные нюансы
- Если аккаунт забанен временно, возвращается `403 Forbidden` с телом:
  `{"message": "Ваш аккаунт заблокирован. Временная блокировка истекает: ...", "banned": true, "bannedUntil": "..."}`
- Если почта не подтверждена, возвращается `403 Forbidden` с телом:
  `{"message": "Ваш email-адрес не подтвержден...", "emailUnverified": true, "email": "ivanov@gmail.com"}`
- Токен содержит в payload: `userId`, `role`.

# GET /api/users/all
## Описание endpoint`а, часть бизнес-логики
Получение списка всех пользователей со статистикой их активности за последние 12 часов и лимитами. Предназначен только для администраторов (панель управления).
## Пример запроса
- **Метод**: `GET`
- **Путь**: `/api/users/all`
- **Заголовки**:
  - `Authorization: Bearer <JWT_TOKEN_ADMIN>`
- **Тело запроса**: Отсутствует
## Пример ответа
- **Статус**: `200 OK`
- **Тело ответа**:
```json
[
  {
    "id": 1,
    "username": "admin",
    "email": "admin@platform.com",
    "role": "admin",
    "created_at": "2026-05-20T10:00:00.000Z",
    "custom_requests": 0,
    "banned_until": null,
    "is_permanently_banned": false,
    "requests_last_12h": 0,
    "remaining_requests": "Unlimited"
  },
  {
    "id": 42,
    "username": "ivan_ivanov",
    "email": "ivanov@gmail.com",
    "role": "Standard",
    "created_at": "2026-05-27T17:50:00.000Z",
    "custom_requests": 2,
    "banned_until": null,
    "is_permanently_banned": false,
    "requests_last_12h": 1,
    "remaining_requests": 3
  }
]
```
## Важные нюансы
- Требуется роль `admin` в JWT-токене, иначе вернется статус `403 Forbidden`.
- Поле `remaining_requests` рассчитывается на лету:
  - Для `Pro` и `admin` — всегда `"Unlimited"`.
  - Для `Standard` и `Lite` — разница между их базовым лимитом (`Standard`: 2, `Lite`: 10) и числом анализов за последние 12 часов, плюс кастомные разовые запросы пользователя (`custom_requests`).

# POST /api/users/moderate-user
## Описание endpoint`а, часть бизнес-логики
Модерация пользователя: временный бан (в часах), пожизненный бан, либо разблокировка (разбан). Доступно только администраторам.
## Пример запроса
- **Метод**: `POST`
- **Путь**: `/api/users/moderate-user`
- **Заголовки**:
  - `Authorization: Bearer <JWT_TOKEN_ADMIN>`
  - `Content-Type: application/json`
- **Тело запроса**:
```json
{
  "userId": 42,
  "action": "temp_ban",
  "durationHours": 72
}
```
## Пример ответа
- **Статус**: `200 OK`
- **Тело ответа**:
```json
{
  "message": "Пользователь успешно смодерирован: temp_ban",
  "user": {
    "id": 42,
    "username": "ivan_ivanov",
    "banned_until": "2026-05-30T17:50:00.000Z"
  }
}
```
## Важные нюансы
- Значения `action`:
  - `perm_ban` — перманентный (вечный) бан. Устанавливает `is_permanently_banned = TRUE`.
  - `temp_ban` — временная блокировка. Рассчитывается время окончания от текущего момента на базе `durationHours` (по умолчанию 24 часа).
  - `unban` — снятие любых блокировок. Сбрасывает флаги и обнуляет даты.
- Любое действие немедленно отключает сессию пользователя при следующем запросе.

## Пример запроса
- **Метод**: `GET`
- **Путь**: `/api/feedbacks`
- **Заголовки**:
  - `Authorization: Bearer <JWT_TOKEN>`
- **Тело запроса**: Отсутствует
## Пример ответа (для обычного пользователя)
- **Статус**: `200 OK`
- **Тело ответа**:
```json
[
  {
    "id": 14,

    "message": "Платформа отличная, транскрибация работает очень быстро!",
```

# POST /api/upload
## Описание endpoint`а, часть бизнес-логики
Загрузка медиафайла (аудио/видео) с локального компьютера пользователя на платформу для последующей транскрибации и ИИ-анализа.
Бизнес-логика проверяет:
1. Авторизацию пользователя.
2. Блокировку (бан).
3. Подтверждение почты (неверифицированные не могут загружать).
4. Тарифные лимиты частоты (rate-limiting). Если лимит исчерпан, тратится кастомный запрос (`custom_requests`), если и их 0 — возвращается статус `429`.

Файл сохраняется локально, создается запись в базе данных в таблице `jobs` со статусом `PENDING`, и задача ставится в очередь RabbitMQ `transcription_jobs`.
## Пример запроса
- **Метод**: `POST`
- **Путь**: `/api/upload`
- **Заголовки**:
  - `Authorization: Bearer <JWT_TOKEN>`
  - `Content-Type: multipart/form-data`
- **Параметры тела (Multipart)**:
  - `mediaFile`: Бинарный файл (аудио/видео, лимит 500 МБ)
  - `language`: Выбранный язык распознавания (`ru`, `en` или `kk`)
## Пример ответа
- **Статус**: `202 Accepted`
- **Тело ответа**:
```json
{
  "message": "Файл принят в обработку",
  "job_id": 105
}
```
## Важные нюансы
- Ограничение по объему файла на бэкенде: 500 МБ.
- Возвращает статус `202 Accepted`, так как операция длительная и выполняется асинхронно в фоновом воркере. Для отслеживания статуса используется WebSocket или опрос статуса по `job_id`.
- При превышении тарифа создается уведомление типа `LIMITS_EXCEEDED`.

# POST /api/upload/youtube
## Описание endpoint`а, часть бизнес-логики
Анализ видео с YouTube по переданной ссылке.
Включает **кеширование на бэкенде**:
- Из ссылки извлекается 11-значный ID видео.
- В базе данных ищется успешно выполненный анализ этого видео (`COMPLETED`).
- **Cache Hit**: Если найдено, создается новый job со статусом `COMPLETED`, данные транскрибации копируются пользователю, и результат отдается мгновенно (статус `200 OK`).
- **Cache Miss**: Если видео новое, запускается стандартный процесс обработки (создается `PENDING` job, задача летит в RabbitMQ) со статусом `202 Accepted`.

## Пример запроса
- **Метод**: `POST`
- **Путь**: `/api/upload/youtube`
- **Заголовки**:
  - `Authorization: Bearer <JWT_TOKEN>`
  - `Content-Type: application/json`
- **Тело запроса**:
```json
{
  "url": "https://www.youtube.com/watch?v=dQw4w9WgXcQ"
}
```
## Пример ответа (Cache Hit)
- **Статус**: `200 OK`
- **Тело ответа**:
```json
{
  "message": "Анализ получен из базы данных (кеш)",
  "job_id": 106,
  "cached": true
}
```
## Пример ответа (Cache Miss)
- **Статус**: `202 Accepted`
- **Тело ответа**:
```json
{
  "message": "YouTube ссылка принята в обработку",
  "job_id": 107
}
```
## Важные нюансы
- Бэкенд поддерживает разные форматы ссылок (`youtu.be`, `youtube.com/watch?v=...`, `youtube.com/embed/...` и др.) и автоматически вытаскивает уникальный ID.
- Воркер реализует **гибридную стратегию**: сначала пытается скачать готовые субтитры YouTube напрямую на выбранном языке. Если субтитров нет, скачивает аудиодорожку и прогоняет ее через Whisper.

# GET /api/search
## Описание endpoint`а, часть бизнес-логики
Глобальный поиск по всем разборам пользователя.
Реализует **кэширование результатов поиска в Redis**:
- Ключ кэша строится индивидуально для пользователя и его запроса: `search:userId:search_query_lowercase`.
- **Cache Hit**: Если в Redis есть запись, она возвращается за микросекунды (флаг `source: "cache"`). Срок действия кэша — 5 минут.
- **Cache Miss**: Поиск в PostgreSQL по подстроке в сыром тексте (`raw_text`) или структурированном JSON-анализе (`structured_analysis`). Для найденных результатов генерируются контекстные вырезки (snippets) длиной до 100 символов вокруг совпадения.

## Пример запроса
- **Метод**: `GET`
- **Путь**: `/api/search?q=физика`
- **Заголовки**:
  - `Authorization: Bearer <JWT_TOKEN>`
- **Параметры запроса (Query)**:
  - `q`: Поисковое ключевое слово или фраза
## Пример ответа
- **Статус**: `200 OK`
- **Тело ответа**:
```json
{
  "source": "database",
  "results": [
    {
      "transcription_id": 23,
      "job_id": 105,
      "snippet": "...лекция по квантовой физике сегодня посвящена основам теории...",
      "created_at": "2026-05-27T17:55:00.000Z"
    }
  ]
}
```
## Важные нюансы
- Поиск регистронезависимый.
- Не возвращает огромный сырой текст полностью ради экономии трафика, а генерирует короткую выжимку `snippet`.

# WebSocket /api/ws
## Описание протокола, часть бизнес-логики
Полнодуплексный канал связи с сервером. Обеспечивает:
1. **Отслеживание статуса задач (Job Subscriptions)**: Фронтенд подписывается на конкретный `jobId` и мгновенно получает статусы (`PENDING` -> `PROCESSING` -> `COMPLETED`/`FAILED`). Сервер проверяет статус каждые 2 секунды.
2. **Получение Push-уведомлений в реальном времени**: При возникновении событий на бэкенде (готовность разбора, лимиты, ответы администрации) Gateway отправляет live-пакет в сокет активным клиентам.

## Пример установления соединения
- **URL**: `ws://localhost:3000/api/ws?token=<JWT_TOKEN>`
- **Важно**: Соединение обрывается со статусом `401/403`, если JWT токен отсутствует или просрочен.

## Входящее событие: Подписка на задачу (Client -> Server)
```json
{
  "type": "subscribe",
  "jobId": 105
}
```

## Исходящее событие: Статус задачи (Server -> Client)
```json
{
  "type": "status",
  "jobId": 105,
  "status": "PROCESSING"
}
```

## Исходящее событие: Live-уведомление (Server -> Client)
```json
{
  "type": "notification",
  "notification": {
    "id": 99,
    "user_id": 42,
    "type": "ANALYSIS_READY",
    "data": {
      "job_id": 105,
      "file_name": "Lecure_Physics.mp3",
      "message_ru": "Анализ файла \"Lecure_Physics.mp3\" готов!"
    },
    "is_read": false,
    "created_at": "2026-05-27T17:55:00.000Z"
  }
}
```
## Важные нюансы
- Соединение привязано к конкретному авторизованному `userId`. Активные сокеты хранятся в памяти API Gateway в виде `Map<userId, Set<WebSocket>>`.
- Опрос статуса завершается автоматически при переходе задачи в финальные статусы `COMPLETED` или `FAILED` (или начинающиеся с `FAILED`).
